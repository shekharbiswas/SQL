# Day 5 Solution: Snowflake vs. dbt vs. DuckDB — Written Comparison

Worked solution for `week4_day5_task.md`, Block 5's core deliverable, plus sample answers for the reading blocks.

## Block 3 — Sample "In Your Own Words" Answer

> Separation of storage and compute means the place data physically lives and the engine that runs queries against it aren't the same thing, and aren't scaled together. In a normal setup — including everything this course has used so far — if you need more query power, you're stuck with whatever the one machine holding your data can provide. Snowflake splits these apart: storage is one shared layer, and any number of independently-sized compute clusters ("virtual warehouses") can point at that same data, scaled up or down, or turned off entirely, without touching the data itself or waiting on each other.

Equivalent objects, one course tool per Snowflake concept:
- Snowflake **database/table** ≈ DuckDB **file/table** (same idea, different scale and hosting)
- Snowflake **virtual warehouse** — no clean DuckDB equivalent; DuckDB has no separable, independently-scaled compute layer at all, since compute is just "whatever the laptop running it has."

## Block 4 — Sample Elastic-Compute Note

> An undersized virtual warehouse means queries queue up or run slowly under load — the data's fine, there's just not enough compute pointed at it. An oversized one runs fast but wastes money, since Snowflake bills for compute time regardless of whether the workload actually needed that much power. DuckDB never faces this trade-off in the same way — there's only one size available (whatever the laptop has), so there's no equivalent decision to get right or wrong; the closest thing this course has done is just waiting longer for a heavy `EXPLAIN`-flagged query in Week 3, Day 3, since there's no "give this query more compute" option locally.

## Block 5 — Model Written Comparison Note

> **dbt.** dbt is a transformation and orchestration tool — it doesn't store any data and it doesn't execute a single query on its own. What it does is generate SQL from a project of `.sql` files, track dependencies between models via `ref()`, run tests, and produce documentation. Week 3's dbt project — `dim_date_spine`, `fct_daily_rides`, `fct_station_weather_volatility` — is a concrete example: dbt organized *what* SQL ran and *in what order*, but every one of those queries still had to be executed by something else.
>
> **DuckDB.** DuckDB has been that "something else" all course — the actual engine storing the data and running every query, whether typed directly in Beekeeper Studio or generated by dbt. It's fast, embedded, and single-machine: everything lives in one file, and compute is whatever the laptop running it provides. There's no separable compute layer to scale independently of storage.
>
> **Snowflake.** If Snowflake replaced DuckDB as this course's engine, what would change is *where* the data lives and *how* queries get executed — data in Snowflake's shared storage layer, queries run by an independently-sized virtual warehouse. What would *not* change is the dbt project itself: the same `sources`, staging models, marts, `ref()` graph, tests, and docs would still apply almost unmodified — only `profiles.yml`'s connection details and the adapter (`dbt-snowflake` instead of `dbt-duckdb`) would need to change.
>
> **Bottom line.** dbt and Snowflake don't compete — they sit at different layers and are commonly used together in production: dbt organizing the transformation logic, Snowflake (or DuckDB, at this course's scale) actually storing the data and running the SQL dbt generates.
